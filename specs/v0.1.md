# v0.1 Specification

## Product statement

A production-oriented health training advisor that uses an Oura-derived health history, explicit user goals and current context to produce an evidence-backed daily training recommendation through an agentic tool-use workflow.

---

## Goal

v0.1 demonstrates the smallest complete version of the platform architecture.

It should show that the project can:

1. authenticate with one real wearable provider
2. obtain and normalize relevant health information
3. expose meaningful health/context operations through MCP
4. let an agent select and use those tools
5. produce a structured daily training recommendation
6. ground that recommendation in evidence
7. evaluate agent behavior deterministically using synthetic scenarios

The goal is not to build a polished consumer application.

The primary showcase is the architecture and engineering of the agentic system.

---

## User experience

The initial interface is a CLI.

A user should be able to request a recommendation for today.

Conceptually:

```text
$ health recommend

Today's recommendation

Activity: Running
Intensity: Easy
Duration: 35 minutes

Reason:
Your recent recovery is below your baseline and your sleep was shorter
than usual, so an easy session is more appropriate than a hard workout.

Evidence:
- ...
- ...

Confidence: 0.82
```

Exact CLI formatting is not part of the contract.

The structured recommendation behind it is.

---

## Provider

v0.1 supports one health provider:

```text
Oura
```

No provider abstraction should be more complicated than necessary, but Oura-specific API models must remain behind a provider boundary.

The domain layer must not depend directly on Oura JSON response shapes.

---

## Authentication

v0.1 must support a working OAuth 2.0 authorization-code flow for Oura.

For local development:

```text
browser
  -> Oura authorization
  -> localhost callback
  -> authorization code exchange
  -> stored access/refresh tokens
```

Requirements:

- authorization-code flow
- CSRF state validation
- localhost callback
- secure handling of client credentials
- secure handling of access and refresh tokens
- refresh-token support
- no tokens in logs or repository files

A known-good local diagnostic probe may be retained outside the production implementation until the production auth flow has been verified against it.

OAuth debugging itself is not a showcase feature.

---

## Health history

The recommendation may use up to approximately 14 days of recent health history.

Initial relevant data includes:

### Sleep

Examples:

- sleep duration
- recent sleep history
- provider sleep observations relevant to recovery

### Recovery

Examples:

- resting heart-rate observations
- HRV observations where semantics are reliable
- provider recovery/readiness information where appropriate

### Training/activity

Recent training may be used when available and useful.

The v0.1 implementation does not need to normalize every field returned by Oura.

Only data required by the recommendation workflow should be implemented.

---

## User input

The recommendation uses explicit user information.

Required conceptual inputs:

```ts
type UserTrainingProfile = {
  goal: TrainingGoal;
  allowedTrainingTypes: TrainingType[];
};
```

The initial goal values are:

```ts
type TrainingGoal =
  | "GENERAL_FITNESS"
  | "ENDURANCE"
  | "STRENGTH"
  | "MUSCLE_GAIN"
  | "WEIGHT_MANAGEMENT"
  | "RECOVERY"
  | "OTHER";
```

For `OTHER`, a short custom goal may be supplied.

Initial training types:

```ts
type TrainingType =
  | "RUNNING"
  | "WALKING"
  | "CYCLING"
  | "STRENGTH"
  | "MOBILITY"
  | "REST";
```

---

## Current context

The recommendation should account for current circumstances in addition to health history.

Initial context:

```ts
type CurrentContext = {
  localTime: string;
  bedtime?: string;
  availableMinutes?: number;
};
```

Examples of desired behavior:

- do not recommend a long workout when only 20 minutes are available
- avoid unnecessarily hard late-evening training when bedtime is near
- allow normal training when recovery and context support it

The exact policy should emerge through agent reasoning plus evaluation rather than through a large hard-coded rule engine.

---

## MCP tools

v0.1 should expose semantic MCP tools.

Expected conceptual tools:

```text
get_user_profile
get_current_context
get_sleep_history
get_recovery_history
get_recent_training
```

Exact names and arguments may change during implementation.

Avoid:

```text
get_all_health_data
```

The agent should retrieve only information relevant to the current decision.

Tool outputs should preserve evidence/provenance.

---

## Agent

v0.1 contains one recommendation agent.

The agent is responsible for:

- obtaining required information through tools
- weighing recent sleep and recovery
- considering the user's explicit goal
- considering current context
- selecting an appropriate training activity
- selecting an appropriate intensity
- proposing a duration when supported
- explaining the reasoning
- attaching evidence
- expressing confidence

The agent must return structured output.

The initial implementation is expected to use the OpenAI Agents SDK.

---

## Recommendation output

Conceptual schema:

```ts
type DailyTrainingRecommendation = {
  activity:
    | "RUNNING"
    | "WALKING"
    | "CYCLING"
    | "STRENGTH"
    | "MOBILITY"
    | "REST";

  intensity:
    | "REST"
    | "EASY"
    | "MODERATE"
    | "HARD";

  durationMinutes?: number;

  targetHeartRateZone?: {
    minZone: number;
    maxZone: number;
  };

  rationale: string;
  evidence: Evidence[];
  confidence: number;
};
```

The exact evidence schema should be defined in the domain package.

Heart-rate targets are optional.

The system must not invent heart-rate zones or BPM values when they are not available from trusted user/provider data or explicitly configured calculations.

---

## Evidence requirements

Every substantive health-based claim in the recommendation must be traceable to available observations.

Evidence should identify enough information to determine:

- what metric or observation was used
- when it was observed
- where it came from
- what value or state influenced the recommendation

The recommendation rationale should be consistent with the evidence array.

The agent must not cite observations that were not returned by tools.

---

## Missing data

Missing health data is a normal condition and must be modeled explicitly.

The agent must not compensate for missing data by inventing measurements.

When important data is unavailable, the recommendation should either:

- rely conservatively on the information that is available
- reduce confidence
- explain the limitation when relevant

Missing data alone should not cause the workflow to fail unless a recommendation cannot be produced safely.

---

## Oura data and AI usage

v0.1 must respect current Oura developer terms for AI/LLM usage.

The implementation must not assume that Oura User Data obtained through the standard REST API may be forwarded directly to an external LLM.

Before the real Oura-to-agent path is implemented, verify the current applicable Oura requirements.

If Oura requires its MCP server for AI use, v0.1 should use the compliant architecture rather than routing REST API data directly into the agent.

The provider integration and domain architecture should remain useful independently of the agent.

---

## Synthetic fixtures

Agent and domain tests must use synthetic or explicitly fabricated health data.

Initial fixture scenarios should include at least:

```text
well_recovered_runner.json
poor_sleep_low_recovery.json
strength_goal_good_recovery.json
late_evening_low_recovery.json
missing_data.json
```

Fixtures should be small, understandable and intentionally designed around specific behavioral expectations.

Real personal Oura exports or API responses must not be committed as fixtures.

---

## Evaluation

v0.1 must include automated evaluation of important agent behaviors.

At minimum, evals should verify that:

### Poor recovery

A scenario containing materially poor sleep/recovery evidence should not result in an unjustified hard workout.

### Healthy recovery

Good recovery should not force unnecessary rest when the user's goal and context support training.

### Context awareness

A recommendation should respect constraints such as limited available time or bedtime being close.

### Grounding

The agent must not invent:

- measurements
- provider scores
- workouts
- heart-rate zones
- evidence

### Evidence consistency

Important claims in the rationale should be supported by returned tool evidence.

### Missing data

Incomplete history should result in conservative reasoning and appropriate uncertainty rather than hallucinated values.

Eval failures should be debuggable through tool-call and structured-output inspection.

---

## CLI

v0.1 exposes the workflow through a local CLI.

The CLI is an integration surface, not the domain architecture.

It should orchestrate the already-defined components rather than contain provider or recommendation logic itself.

Conceptual commands may eventually include:

```text
health auth login
health auth status
health recommend
```

Exact command names are not fixed by this specification.

---

## Persistence

v0.1 should implement only the persistence required to make the local workflow usable.

Token persistence is required for OAuth usability.

Health-data caching is optional and must not be added until provider retention/caching requirements have been checked.

Application-owned state such as user goals and context may be stored locally when useful.

The domain model must not depend directly on a specific database.

---

## Security and privacy

v0.1 must follow these minimum rules:

- no secrets in source control
- no OAuth tokens in source control
- no raw personal health data in committed fixtures
- avoid raw health data in logs
- use least-privilege provider scopes where practical
- sanitize diagnostic output
- do not expose secrets to the agent
- do not include credentials in traces

The local development workflow may use platform credential storage or another appropriate secret-management mechanism.

---

## Implementation approach

v0.1 should be implemented as small vertical slices.

A likely progression is:

```text
health domain
    -> synthetic fixture
    -> Oura provider boundary
    -> normalization
    -> MCP tools
    -> recommendation agent
    -> evals
    -> CLI integration
```

Do not scaffold future applications or SDKs before they are needed.

Each implementation step should keep the repository in a coherent and testable state.

---

## Definition of done

v0.1 is complete when all of the following are true:

1. Oura OAuth works through the production implementation.
2. Relevant Oura health information can be obtained through the provider boundary.
3. Required observations can be represented in the normalized health domain.
4. User profile and current context are available to the workflow.
5. The agent obtains information through semantic MCP tools.
6. The agent returns a validated structured daily recommendation.
7. The recommendation includes traceable evidence.
8. Synthetic evals cover grounding, recovery, context and missing-data behavior.
9. The workflow is usable through a local CLI.
10. No real personal health data, OAuth tokens or client secrets are committed to the repository.

---

## Explicit non-goals

The following are outside v0.1:

- Polar integration
- additional wearable providers
- Swift SDK
- Kotlin SDK
- iOS application
- Android application
- web dashboard
- cloud deployment
- multi-user authentication
- conversational coaching
- persistent conversation history
- long-term adaptive training plans
- learning from user feedback
- automatic plan adjustment across weeks
- medical diagnosis
- treatment recommendations
- medical-device functionality

These may be explored in later versions without expanding the scope of v0.1.
